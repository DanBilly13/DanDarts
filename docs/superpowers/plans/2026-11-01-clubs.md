# Clubs Implementation Plan

> **For agentic workers:** use superpowers:subagent-driven-development (or superpowers:executing-plans) to run this plan task by task. Steps use checkbox (`- [ ]`) syntax. Spec: `docs/superpowers/specs/2026-11-01-clubs-design.md`. Mockups: artboards 18-24 in the "DartFreak App Screens" Design artifact.

**Goal:** Players can create and join clubs (Open or Invite-only), get friend suggestions from shared clubs in the Friends tab, and join a club during sign-up, on iOS first and then Android, with reporting and light moderation in place.

**Architecture:** A Supabase backend of five new tables, triggers and `SECURITY DEFINER` RPCs (clients never read member lists directly); a new `ClubsService` on iOS and `ClubsRepository` on Android mirroring the friends code; a Clubs tab; a website landing page for club links.

**Tech Stack:** Postgres/Supabase (SQL migrations applied by hand), Next.js website (`DartFreak-Web`), SwiftUI, Kotlin/Compose, Firebase Analytics.

---

## Ground rules

- **Migrations are additive and applied by hand** in the Supabase SQL editor against the live database; there is no staging copy. Run every migration first inside `BEGIN; ... ROLLBACK;` to prove it applies, then run it again with `COMMIT;`. Never drop or rewrite an existing table or policy. Use `IF NOT EXISTS` / `DROP ... IF EXISTS` for idempotency, as the existing migrations do.
- Next free migration number is **093**. Header, `BEGIN/COMMIT`, `RAISE NOTICE` style as in `091_pin_save_remote_visit_search_path.sql`. Every function: `SECURITY DEFINER`, `SET search_path = public`, then `REVOKE ALL ... FROM PUBLIC; GRANT EXECUTE ... TO authenticated`.
- One branch and one PR per task group, off the main line (`test-flight` for iOS and the backend, `master` for Android). Never `git add -A`. Commit messages end with the `Co-Authored-By` line. Push, open a PR and merge only when asked; every PR gets a real review (`/code-review`) before it is merged.
- Don't touch the user's `/Users/dan/Projects/DanDarts` folder while they might be archiving; work in a git worktree.
- Version bumps (iOS build number, Android `versionCode`) are separate tiny commits made only when a build is requested.
- Backend ships first and alone; apps ship after it is live. The backend must not change what current app versions see.

## Phase A: Backend

### Task 1: Tables and helpers (093)

- [ ] Create `club_normalize(text)` (lower case, `unaccent`, punctuation stripped, spaces collapsed; `CREATE EXTENSION IF NOT EXISTS unaccent` first and confirm it exists in this project) and `generate_club_code()` (6 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, loop until unique).
- [ ] Create `clubs`, `club_members`, `club_suggestion_dismissals`, `reports`, `blocked_words` exactly as in the spec's data model, plus the partial unique index on Open clubs, and `ALTER TABLE users ADD COLUMN IF NOT EXISTS club_discoverable boolean NOT NULL DEFAULT true`.
- [ ] Dry-run in a transaction with rollback, then apply. Check: existing app still reads `users` fine (the new column has a default).

### Task 2: Triggers (094)

- [ ] `member_count` maintenance on `club_members` insert/delete.
- [ ] Limit of 5 clubs per user on `club_members` insert (raise `club_limit`).
- [ ] After delete on `club_members`: if the club has members but no admin, promote the oldest `joined_at`; if no members, delete the club.
- [ ] Check with a scratch club in the rolled-back transaction: leave as admin, remove the last member, delete a user.

### Task 3: RLS (095)

- [ ] Enable RLS on all five tables. `is_club_member(club_id)` helper (`SECURITY DEFINER`, `SET search_path = public`). `clubs` and `club_members` SELECT only for members; no client INSERT/UPDATE/DELETE policies. `reports` INSERT where `reporter_id = auth.uid()`. `club_suggestion_dismissals` SELECT/DELETE own rows. `blocked_words` no client access.
- [ ] Check as an authenticated test user that a non-member reads nothing.

### Task 4: Core RPCs (096)

- [ ] `create_club`, `search_clubs`, `get_club_preview`, `join_club`, `join_club_by_code`, `leave_club`, each returning a result code (`ok`, `full`, `invalid_code`, `name_not_allowed`, `duplicate`, `not_authenticated`, ...) like `claim_invite`. `search_clubs` returns Open clubs only, 20 rows, most members first. `get_club_preview` returns name, town, visibility, member count and up to 3 avatars, excluding members with `club_discoverable = false`.
- [ ] Name filter: `create_club` rejects a normalised name that contains any `blocked_words` entry.

### Task 5: Admin and suggestion RPCs (097)

- [ ] `set_club_visibility` (admin only; Open collision returns `duplicate`), `regenerate_club_code`, `remove_club_member`, `club_members_list` (members only, includes the friendship state with the caller), `club_suggestions(p_limit)`, `dismiss_club_suggestion`, `report_content`.
- [ ] `club_suggestions` exclusions exactly as in the spec: me, anyone I have any friendship row with (any status, either direction), anyone with `club_discoverable = false`, anyone I dismissed. Order by shared clubs, then most recent join.

### Task 6: Friend-request cap (098)

- [ ] `BEFORE INSERT` trigger on `friendships`: count rows with this `requester_id` and `created_at > now() - interval '24 hours'`; at 50 or more raise `friend_request_limit`. Keep the limit in one constant in the function.
- [ ] Check that `claim_invite` still works under the cap and surfaces a readable error.

### Task 7: Verification script and seed data

- [ ] `VERIFY_clubs.sql`: create/join/leave, the 5-club limit, admin promotion, empty-club cleanup, deleting an account that owns a club, suggestion exclusions, the cap, and that a non-member cannot read members. Roll back at the end.
- [ ] Insert a short starter `blocked_words` list (the owner reviews it).
- [ ] The owner creates 10-20 real clubs by hand through the app once it ships (not through SQL).
- [ ] PR to `test-flight`: migrations plus verify script. Review, merge, then apply to the live database in order 093 to 098.

## Summary (PR body template)

Adds Clubs: Open and Invite-only clubs, friend suggestions from shared clubs, a Clubs tab, club links, reporting and a name filter, and an "I'm 13 or over" tick-box at sign-up. Backend first (migrations 093-098), then website, iOS and Android.

## Known limits

- Reports are reviewed by hand in the Supabase SQL editor; there is no moderation screen.
- The name filter is a small word list the owner maintains.
- Clubs have no photos, chat, stats or several admins in v1 (see the spec's Out of scope).
- The friend-request cap and club limit are judgements to revisit after launch.

## Test plan

- `VERIFY_clubs.sql` passes in a rolled-back transaction before each migration is applied for real.
- Unit tests: models, result-code mapping, analytics schema, name validation.
- Manual with three test accounts on both platforms: create, find, join, share, open links with and without the app, suggestions, dismiss, report, leave as admin, delete an owner's account, hit the 5-club limit, sign up with email, Google and Apple (iOS) with the tick-box.
